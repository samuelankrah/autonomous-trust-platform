# Phase 1 Acceptance Tests

Status: DRAFT for owner approval, Phase 0 design document, not an implementation authorization.

## Preamble

These tests gate Phase 1 acceptance. Failing any one test blocks acceptance until the failure is fixed, or the scope is formally reduced by the owner (Samuel). A partial pass, a verbal assurance, or a successful demonstration on a different scenario does not substitute for a pass on the test as written.

Scope: These tests gate the Phase 1 build as scoped in the owner-approved Phase 0 plan, namely the single payments report scenario across the Explore, Operate, and Architect levels. Any reduction to that scope is by owner record only, and it amends the affected tests, consistent with the acceptance rule restated at the end of this document.

Each test below gives: an identifier (ID), setup, action, pass condition, and evidence artifact produced (the recorded proof that the test was run and what happened). Evidence artifacts are retained with the run record, not held only in memory or in chat.

Conventions used in every test:

- Plain words first: Any shortened technical term is expanded in plain words at first use in the test record.
- Engine grounding: All behavior is that of the verified reference engine in labs/decision-service. The seven scenarios are: happy-path, identity-no-authority, revoked-delegation, stale-attestation, tampered-decision, replayed-decision, bypass-attempt. Decisions are PERMIT (allowed), DENY (not allowed), and INDETERMINATE (cannot be decided safely from the evidence available). The attestation freshness threshold is a synthetic lab constant of 300 seconds, labeled non-normative (not an official rule for real systems). Revocation uses a seeded list (a prepared list of withdrawn grants).
- Primary learner: Samuel, for learner facing tests, unless a test states otherwise.
- No test may be passed by broadening authority, inventing a capability, or relabeling simulated behavior as reference-tested behavior.

## AT-01: Beginner start without specialized vocabulary or a design record

Source criterion: Beginner start without Identity and Access Management vocabulary or reading an Architecture Decision Record (primary learner narrates). Identity and Access Management means the field of managing who things are and what they may do, shortened in this document only after this expansion. An Architecture Decision Record is a short written record of a design choice and its reasons.

- ID: AT-01
- Setup: A fresh workshop state for the payments report scenario (in the engine: workload payments-reporter, resource /reports/quarterly, action READ). No prior journey completed in this state. No glossary preopened, no design record shown.
- Action: The primary learner (Samuel) starts the journey at the Explore level and proceeds through the component story walk and the happy path step-through, narrating aloud (or in recorded text) what each component does and what they expect to happen, without being given specialized vocabulary in advance and without opening any Architecture Decision Record.
- Pass condition: The learner reaches the end of the Explore happy path, correctly names the purpose of each of the eight components in plain words (workload, identity, grant, attestation evidence, decision point, enforcement point, protected resource, evidence ledger), and records a correct prediction for the happy path outcome before it is revealed, all without the interface requiring specialized vocabulary or a design record to proceed. Any place where the learner was blocked by unexplained jargon is a failure, even if the journey was eventually completed with help.
- Evidence artifact produced: The narration record (audio transcript or text log) timestamped to journey steps, plus the recorded prediction for the happy path, plus a jargon block log listing every term the learner flagged or stumbled on (an empty log is a valid artifact, if true).

## AT-02: Inspect and manipulate critical components on a phone

Source criterion: Inspect and manipulate critical components on a phone.

- ID: AT-02
- Setup: A representative device and viewport matrix with three targets: (1) the primary target, a small Android phone class viewport of 360 by 800 CSS pixels, Chrome on Android, touch input, TalkBack available; (2) a large Android phone class viewport of 412 by 915 CSS pixels, Chrome on Android, touch input; (3) an iPhone class viewport of 390 by 844 CSS pixels, Safari on iOS, VoiceOver available. Each target is run on a device or emulator of its class, and the run record captures, for every target run: browser and operating system, viewport dimensions, zoom and text scaling (the matrix is tested at 100 percent and at 200 percent text scaling), input method, and the assistive technology used. Fresh workshop state, payments report scenario loaded, happy path baseline confirmed by a stepped run.
- Action: On the phone, the learner opens the inspector sheet for each critical component (workload, identity, grant, attestation evidence, decision point, enforcement point, protected resource, evidence ledger) and reads its purpose, current state, inputs, outputs, authority, and failure behavior. An inspector answer that does not apply to a component in this scenario, or that the engine does not have, may be given explicitly as "not applicable in this scenario" or "not modeled", with a provenance label of engine-observed, workshop explanation, or not modeled; such an explicitly labeled answer counts as a present section. The learner then applies at least one manipulation from the control panel and observes the changed component state in words on the component view.
- Pass condition: The full inspection and manipulation sequence completes successfully on the primary target (small Android phone class), with the matrix details recorded for every target run. Every inspector sheet opens and is fully readable on the phone, every section is present in plain words (an explicit "not applicable in this scenario" or "not modeled" answer with its provenance label counts as present; an invented detail is a failure, and an honest not-modeled label is not), every action is completable by button (no gesture only action), and at least one manipulation visibly changes the labeled state of the affected component in words (icon plus text, never color alone). Accessibility verification targets, all required: text scales to 200 percent without loss of content or function (content reflows, with no essential two-dimensional scrolling); every action is operable by keyboard and by switch navigation; focus order matches reading order; focus returns to the invoking component row when an inspector sheet closes; all controls carry screen-reader labels, and decision states are announced per the wireflow. Any component that cannot be inspected, any manipulation that cannot be applied, or any accessibility target missed, on the phone is a failure.
- Evidence artifact produced: A per component inspection checklist signed off during the run, with the full matrix record for every target run (browser and operating system, viewport dimensions, zoom and text scaling, input method, assistive technology used), plus a screen by screen capture set (screenshots or a structured screen log) showing each inspector sheet, each not applicable or not modeled answer with its provenance label, and the post manipulation state labels.

## AT-03: Prediction occurs before outcome disclosure, enforced by the interface

Source criterion: Prediction occurs before outcome disclosure, enforced by the interface.

- ID: AT-03
- Setup: Fresh workshop state. Test tooling or inspection access sufficient to verify that no outcome is rendered, announced, or present in the reading order before a prediction is recorded. At least two scenarios prepared: happy-path and one fault scenario (revoked-delegation or stale-attestation).
- Action: Attempt, by every available input method including assistive technology navigation and any continuous play control, to reveal a decision or enforcement outcome without recording a prediction (both choices plus a reason, per the wireflow predict gate). Then record a prediction and run, and verify the prediction is shown unchanged beside the outcome. Repeat for the second scenario.
- Pass condition: In both scenarios, no decision, enforcement result, trace outcome, or evidence outcome is disclosed by any path before a complete prediction is recorded. After the run, the recorded prediction matches the pre-run record exactly (it was not edited after disclosure). Any leak path, including a reading order leak or a pre-rendered trace, is a failure.
- Evidence artifact produced: A gate test log listing each attempted bypass path and its result, the timestamped prediction records, and the post run comparison showing each prediction beside its outcome, unedited.

## AT-04: Break, diagnose, and repair for each of the five fault classes, without broadening authority

Source criterion: Break, diagnose, repair for each of the five fault classes, without broadening authority.

- ID: AT-04
- Setup: Fresh workshop state, happy path baseline confirmed. The five fault classes, matching the five contract-supported manipulations and engine scenarios, are: (1) revoked grant (revoked-delegation), (2) stale attestation (stale-attestation), (3) tampered decision (tampered-decision), (4) replayed decision (replayed-decision), (5) bypass attempt (bypass-attempt).
- Action: For each fault class, in turn: apply the single manipulation, record a prediction, run stepped with pause-and-inspect, diagnose by naming the fault and the stage that caught it, repair, record a fresh prediction, and rerun. A repair is defined uniformly: the repair is performed as a NEW RUN whose configuration is a reset clone of the happy path baseline with the single fault removed; the failed run is never mutated, and its trace and ledger entries are preserved as evidence. Per fault, the repair new run is configured as follows: revocation repair means the new run's grant is absent from the revocation list; stale repair means a new run with freshly issued attestation (the clock is not advanced); tamper repair means a new run presenting the untampered decision; replay repair means a new run in which a fresh decision is obtained for the second request through the normal decision step and enforced, with the original replay rejection preserved as evidence; bypass repair means, after diagnosis, executing the normal request path (decision, then enforcement) in a new run to demonstrate restoration. After each repair, compare the restored grant, resource, and action to the happy path baseline.
- Pass condition: For all five classes, the engine outcomes match the contract: revoked gives decision DENY; stale gives decision INDETERMINATE and enforcement DENY_INDETERMINATE; tampered gives enforcement REJECTED with a signature reason; replayed gives first use ALLOWED and replay REJECTED with a binding reason; bypass gives BYPASS_BLOCKED with the attempt recorded in the ledger. In every case the protected operation is not invoked on failure. Every diagnosis names the correct fault and stage. Every repair is a new run as defined above (the failed run unmutated, its trace and ledger entries preserved), restores the happy path outcome, and the post repair permission comparison, which compares structured values (grant scope fields, resource, action) to the baseline rather than display text, shows them identical to the baseline (resource /reports/quarterly, action READ), with no broader authority. Any class failing any part, or any repair that adds permission, is a failure of this test as a whole.
- Evidence artifact produced: A five row fault matrix, one row per class, each row containing the fixture file and contract version used, the manipulation applied, the recorded predictions (fault run and repair run), the observed decision and enforcement results, the diagnosis text, the repair action, the rerun outcome, and the authority comparison result, plus the evidence ledger extracts for each run (including the preserved failed runs).

## AT-05: Parity with golden fixtures under the scenario contract

Source criterion: Parity: every rendered trace matches its golden fixture under docs/workshop/fixtures/ (scenario contract v1).

- ID: AT-05
- Setup: Golden fixtures present under docs/workshop/fixtures/ for scenario contract version 1 (v1), covering all seven engine scenarios, generated from the verified reference engine (seeded, deterministic runs) and version labeled. Fresh workshop state. The fixture version under test is recorded before the run.
- Action: For each of the seven scenarios, run the workshop journey stepped to completion (with predictions recorded, per AT-03 discipline, but judged here only on trace parity), capture the full structured decision trace, and compare it to the corresponding golden fixture under the canonical parity projection stated in the pass condition below. The comparison runs on structured trace data before rendering; display mappings never alter the normative strings.
- Pass condition: Parity is judged under the following canonical parity projection. Compared exactly (byte for byte for strings, structural equality for objects, order significant for arrays):
  - contract_version, scenario, seed.
  - requirement_ids (same IDs, same order).
  - verdict PASS.
  - checks (same count and order; per row check_id exact, requirement_ids same and in order, passed boolean equal per row, detail compared byte for byte).
  - inputs principal/resource/action/workload_path.
  - inputs.requests in creation order with request_id and nonce exact (null equal only to null).
  - inputs identity/grant/attestation objects field for field including timestamps, key_id, signature_present, with grant constraints and provenance compared as structured mappings.
  - inputs revoked_grant_ids and clock_advances_seconds as lists.
  - inputs.direct_access exact or null.
  - decision and decisions (count and order; field for field: decision_id, request_id, state, principal, workload, resource, action, authority_provenance as structure with null equal only to null, policy_id, policy_version, freshness ages exact including null, validity window exact, transaction_binding exact, reason exact string byte for byte, key_id, signature_present).
  - enforcements (count and order; via; presented request_id and nonce exact; presented_decision compared field for field under the same rule, null for direct_access, and for tampered-decision this is the altered decision as presented; outcome field for field: outcome_id, decision_id (null for bypass), request_id, result, reason exact string byte for byte, enforced_at; operation_result exact, null when not invoked; replayed-decision therefore compares two enforcements, first ALLOWED and second REJECTED).
  - evidence.event_types (same list, same order).
  - evidence.events (count and order; type exact; field-name set per event exactly equal; seq field name present on every event and the implementation's seq values integers forming a contiguous sequence in event order; prev_hash and record_hash field names present, their values outside parity).
  Outside parity: signature values, key material, hash values, wall-clock durations, rendered or display text. There is no partial parity: any mismatch on any compared element fails the test for that scenario. Any scenario without a fixture is a failure. A fixture that does not itself trace to a seeded reference engine run is also a failure, and must be reported as a fixture defect, not waived.
- Evidence artifact produced: A parity report listing, per scenario, the fixture file name and contract version, the comparison result per field, and a diff for any mismatch, plus the seeded run identifiers used to generate or regenerate the fixtures.

## AT-06: Memory anchors, delayed recall, and transfer, recorded in the Study Lab ledger

Source criterion: Memory: approved anchors with counterexample and teach-back; delayed recall and a transfer check recorded in the Study Lab ledger.

- ID: AT-06
- Setup: The five memory anchors from the memory anchor specification, named as: authentication versus authorization, attestation freshness, revocation, decision integrity check, replay binding (note the rename: the fourth anchor was formerly named signature integrity and is now decision integrity check). Only owner-approved anchors participate in learner recall. Draft anchors appear only in an owner review flow visibly marked DRAFT, or are omitted entirely; they never appear as learner recall items. If any anchor is still DRAFT at test time, this test cannot pass and the run records that as the blocking reason. Study Lab ledger (the per-learner progress record) ready to receive entries.
- Action: For each approved anchor: run the immediate recall check (predict and explain right after exploration), the later in session retrieval (visual aid and cue hidden), a delayed retrieval in a later session (reduced hints, scheduled on the Study Lab ledger's existing fixed interval ladder of 1, 2, 5, 12, 25 days), and a transfer check (a changed scenario requiring application, not repetition). Collect the teach-back for each anchor, including what the cue captures and what it omits, and the counterexample statement. Adaptive, performance-adjusted scheduling is deferred as a Phase 1 design gate and is not an acceptance criterion for this test; no scheduling claim in this test asserts validated learning science.
- Pass condition: For every anchor, the ledger contains: the approved wording reference, the anchor wording version recorded alongside approval status and each check result, a behavioral test pass (correct prediction plus correct reason, per the anti-mnemonic-theater rule, meaning no credit for cue recitation alone), a counterexample in the learner words, a teach-back record, a delayed recall result obtained on the fixed interval ladder (1, 2, 5, 12, 25 days), and a transfer check result. Missing any element for any anchor is a failure. A delayed recall that showed the cue first is recorded as invalid and does not count.
- Evidence artifact produced: The Study Lab ledger extract for the test period, showing per anchor entries for approval status and anchor wording version, immediate, later, delayed, and transfer checks with outcomes, teach-back references, and the ladder intervals applied.

## AT-07: Honest labels, simulated versus reference-tested, with no production claims

Source criterion: Honest labels: behavior displays carry one of the four defined labels visibly distinguished; no production or enforcement claims anywhere in the experience.

- ID: AT-07
- Setup: Full journey available across all three levels (Explore, Operate, Architect) and all screens in the wireflow. A text search facility for all learner facing strings in the experience under test. The label taxonomy has exactly four labels, defined as follows: simulated (modeled in the workshop interface); reference-tested (produced by the verified reference engine, and only when bound to a named reference run: scenario, seed, and contract version); conceptual explanation (teaching copy or analogy, not behavior); not modeled (a capability or fact the engine does not have).
- Action: Inspect every screen, sheet, trace, and evidence view and record its label from the four label taxonomy (simulated, reference-tested, conceptual explanation, or not modeled). For every display labeled reference-tested, record its named reference run binding (scenario, seed, and contract version). Search all learner facing text for production or real enforcement claims, including claims of real identity issuance, real policy enforcement, real key management, suitability for production use, or that a lab constant (including the 300 second freshness threshold) is a real world rule. Cross-check a sample of reference-tested labels against actual engine runs.
- Pass condition: Every behavior display carries one of the four taxonomy labels in words. A display labeled reference-tested without a named reference run binding (scenario, seed, and contract version) is a failure. No learner facing text claims production behavior, real enforcement, or real world validity for lab constants, in any level or screen. Every sampled reference-tested label corresponds to a behavior the engine actually performs in the named scenario. Any unlabeled display, any mislabeled display, or any production claim anywhere is a failure.
- Evidence artifact produced: A label audit table listing each screen and view with its label (and, for reference-tested displays, its named reference run binding) and a verification mark, the full text search terms used and their hit list (with disposition for each hit), and the engine cross-check sample with scenario names and outcomes.

## AT-08: No sign-in or infrastructure required for the first learning journey

Source criterion: No sign-in or infrastructure required for the first learning journey.

- ID: AT-08
- Setup: A clean state representing a first time learner: no account created, no sign-in performed, no identity provider connected, no database connected, no external application programming interface connected, and no credential provisioned for this journey. Static network serving of the workshop is allowed: a static host serving files is not external infrastructure for this test, and the delivered workshop may be served over a network. Account and connection state at start are recorded.
- Action: The primary learner completes the entire first learning journey (Explore happy path plus at least one full Operate break, diagnose, repair cycle, ending with teach-back) from first open to finish, without signing in, creating an account, entering any credential, and without the journey requiring any external identity provider, any database, or any external application programming interface.
- Pass condition: The journey completes end to end in the clean state. At no point does the experience require, prompt for, or block on a sign-in, an account, a credential, an external identity provider, a database, or an external application programming interface. Static network serving of the workshop files does not fail this test. Offline capability is recorded as a separate, non-required note in the run log and is not a pass condition. If any prohibited requirement appears, even if it can be dismissed, the point of appearance is recorded and the test fails until the requirement is removed from the first journey path. Optional, clearly separated later features that are not on the first journey path do not fail this test, provided they are never presented as required.
- Evidence artifact produced: A clean state run log showing start state (no account, no sign-in, no external identity provider, database, or external application programming interface connected), each journey stage completed in order, every prompt encountered with its disposition, the non-required offline capability note, and the teach-back record proving the journey reached its defined end.

## Acceptance rule restated

All eight tests, AT-01 to AT-08, must pass for Phase 1 acceptance. A failure in any one blocks acceptance until it is fixed and retested, or the owner formally reduces the scope in writing and the affected test is amended to match the reduced scope, with the amendment recorded beside the original test.
